# Verified GPU lifecycle and persistent model storage — 21 October 2026

Scope: TrustFolio **Washing Machine pilot only**. This is provider research and architecture, **not** credential provisioning, GPU rental, scene rendering, TTS expenditure, or publishing.

## Hostinger decision: cannot meet full lifecycle automation
Hostinger has no verified publicly supported create/list/destroy GPU instance API or GPU CLI. Standard-VPS API and application deployment over SSH do **not** imply GPU infrastructure lifecycle automation. GPU-attached disk is ephemeral: destroying the instance destroys weights and video work files. Hostinger GPU can be used **manually** only; do not create a misleading GitHub GPU-create workflow using VPS endpoints. User-provided Hostinger documentation:
- https://www.hostinger.com/support/how-to-choose-between-a-hostinger-vps-and-gpu-instance/
- https://www.hostinger.com/support/11679133-how-to-use-hostinger-api-cli/
- https://docs.hostinger.com/api-reference/overview
- https://www.hostinger.com/in/gpu-hosting

## RunPod choice: official API v2 + network volumes VERIFIED in documentation
Official API v2 documents:
- Create Pod (POST): https://docs.runpod.io/api-reference-v2/pods/create-a-pod
- List Pods (GET): https://docs.runpod.io/api-reference-v2/pods/list-pods
- Terminate Pod (DELETE): https://docs.runpod.io/api-reference-v2/pods/terminate-a-pod
- Create Network Volume (POST): https://docs.runpod.io/api-reference-v2/network-volumes/create-a-network-volume
- Network volume vs ephemeral disk: https://docs.runpod.io/pods/storage/types
- Published pricing: https://www.runpod.io/pricing
RunPod REST API v2 is currently in public beta; verify the pinned schema and exact payload before live provisioning.

A network volume has an independently billed lifecycle: the Pod can be destroyed while approved model weights remain on the volume. The network volume **must be selected during Pod creation** and is datacenter-bound; not all GPU offers are compatible with a given volume, and capacity must be checked live. Distinguish volume disk from network volume; the former is destroyed with the Pod.

## Candidate resource sizing (NOT a provisioning instruction)
- Wan2.2 TI2V-5B: ~24GB NVIDIA GPU memory required as documented by the upstream project; 24GB might still OOM in practice, so test with a constrained 5-second clip and use model offloading before considering a larger GPU.
- Approved model, working assets, Hindi audio and intermediates: **100GB standard Network Volume is a tentative capacity target**, not a committed purchase. Measure model download sizes, lip-sync checkpoint sizes, cache/intermediate needs and free space first.
- RunPod public advertised examples as of Oct 8, 2026: RTX 3090 24GB $0.50/h, RTX 4090 24GB $0.89/h, RTX A6000 48GB $0.59/h. **Price on a specific volume-compatible GPU at deploy time may differ**; DO NOT assume 3090/4090 listings are available in compatible region.
- Standard network volume under 1TB: $0.07/GB/month (100GB ~$7/month while it exists). Other transfer/storage, tax or conversion costs may apply.
- No guaranteed zero cost or preapproved run.

## Proposed future workflow (ALL PROVISIONING/PUBLISHING DISABLED)
1. GitHub CPU-only workflow validates package generated by `scripts/package_gpu_job.py`, original SHA256 assets and **approved** natural Hindi MP3. Existing `washing-gpu-input-preflight.yml` already does CPU-only plan/tests.
2. Controller retrieves a least-privilege RunPod key from GitHub Actions secrets (NEVER commit it). Before a charged action, validate spend cap, Pod limit=1, network volume existence, GPU compatibility, maximum runtime and preflight input completeness.
3. Provision API v2 Pod *with* existing network volume. Read-only pin specific Wan source revision and validated exact model checkpoint hashes. Stage job and assets via scoped credentials; never overwrite pinned master assets.
4. Generate **only one** silent Washing Machine scene and test its character consistency, duration, resolution, and hardware cost.
5. Later add Hindi lip-sync and remaining storyboard scenes only after shot-level QA. Muxing audio with ffmpeg alone does **not** count as lip-sync.
6. Upload MP4 plus SHA256/QA logs to durable object storage and optionally a GitHub Actions artifact. Confirm remote checksum and availability **before** success is recorded.
7. Always terminate Pod in error/cancel/timeout paths (finally + independent stale-Pod janitor). Re-query pod list and billing to **verify** deletion; don't infer deletion merely because a DELETE request was sent. Keep the Network Volume deliberately for next run. Storage remains billed while idle.
8. Publishing stays OFF. The user's VPS may later send a GitHub dispatch; VPS itself does no GPU work.

## What is verified vs outstanding
Verified from official **public documentation**: RunPod API v2 Pod create/list/delete and persistent Network Volume endpoints; published pricing and storage survival.

Not verified in user's account: RunPod connection, permissions, regional 24/48GB compatible GPU availability, checkout rates, budget enforcement, any live GPU render, natural Hindi TTS MP3, true cartoon lip-sync or automated termination. No RunPod API key was used, no network volume or paid GPU was created.

Alternatives: Vast.ai also documents REST API offer search, instance creation, list and destroy (https://vast.ai/developers/api), but for this specific *avoid repeated model transfers* requirement, RunPod Network Volume is a simpler documented fit. Re-evaluate Vast.ai if the compatible RunPod region lacks supply or costs more than the agreed budget.
